# გვარები — Georgian Surname Atlas (prototype)

A static dashboard for the distribution of Georgian surnames: search a surname and
see where it concentrates, open a municipality and see what is distinctive there,
or browse the national rankings. No server, no database — a build script writes a
static payload and the browser does the rest.

Runs on the voter roll: 69,290 surnames across 3,563 precincts, aggregated to
66 municipalities and 75 electoral districts. Nothing below municipality is ever
published — see the suppression notes below.

```bash
npm install
npm run tiles          # one-time: cache the Georgia basemap (~7 MB)
npm run dev            # http://localhost:5173
```

`npm install` and `npm run tiles` are the only steps that need a network. After
them the app is entirely self-contained — fonts, basemap, payload and all — and
`OFFLINE=1 npm run inspect` proves it by making DNS fail for every host except
the local server.

---

## Layout

```
build/build.R          the whole pipeline: five CSVs -> static payload
data/input/            sample inputs, in the shape build.R expects
public/data/           the payload the app fetches (generated; committed for the demo)
public/tiles/          cached basemap (generated by `npm run tiles`; gitignored)
src/
  fonts/               self-hosted Noto Sans Georgian (generated by `npm run fonts`)
  lib/                 state, data loading, metrics, colour scales, i18n, KDE painting
  components/          map, header, control rail, layer panel, legend
  views/               surname, region, explore, method
tools/                 headless checks (see below)
```

## Working on it

| command | what it does |
|---|---|
| `npm run dev` | dev server with hot reload |
| `npm run build` | production build into `dist/` |
| `npm run data` | re-run the R pipeline over `data/input` into `public/data` |
| `npm run tiles` | cache the Georgia basemap into `public/tiles` (needs a network) |
| `npm run fonts` | refresh the self-hosted font files and their `@font-face` block |
| `npm run check` | validate the payload and the metric logic (no browser needed) |
| `npm run inspect` | open a route in headless Chromium and report console errors |

`tiles` and `fonts` are the only two that talk to the outside world, and both
are idempotent — they skip what is already cached. `inspect` takes `OFFLINE=1`
to make every host but localhost unresolvable, which is how the offline claim
above is checked rather than assumed.

`npm run check` is the one to run after touching the build script or the metrics.
It verifies that every indexed surname resolves to its bucket, that no published
cell is below the suppression threshold, that district and municipal totals
reconcile, that every density cell is inside the grid, and that the two locale
files have identical key sets with matching placeholders.

## Swapping in the real data

1. Replace the five files in `data/input/` — the contract is in `data/README.md`.
2. Replace `public/data/geo/*.geo.json` with real boundaries. The only requirement
   is that each feature's `id` equals the area `code` in `areas.csv`.
3. `npm run data && npm run check`.

Nothing in `src/` should need to change. If it does, the contract is wrong and
worth fixing rather than working around.

## What the pipeline guarantees

`build/build.R` is the only thing that ever reads precinct-level counts. It:

- folds spelling variants via `merge_into` before anything else sees them;
- derives transliterations and suffix families, letting `surnames_meta.csv` override;
- **suppresses every surname × area cell below k = 5**, and applies complementary
  suppression so a lone withheld cell cannot be recovered by subtraction from the
  published national total;
- rasterises each surname to a Gaussian kernel density estimate on a fixed
  200 × 110 grid, weighted by each precinct's electorate so the surface shows
  concentration rather than population, floors the tail to zero, and quantises to
  one byte per cell.

Precinct coordinates and counts are consumed there and never written out. No
asset, endpoint or tooltip can return a precinct value, because none of them
contains one.

## Notable decisions

**MapLibre, not d3-geo.** Once a basemap is in play, hand-rolling tiles, zoom and
projection stops being lighter than the library.

**The basemap ships with the repo.** `npm run tiles` caches Esri's World Light Gray
canvas for the Georgia bounding box (z0-11, ~1,700 tiles, ~7 MB) into `public/tiles`,
and `MapView.svelte` reads from there. No key, no quota, no third-party outage, and
the map works with the network unplugged.

Not CARTO, which is what this pointed at originally. Its keyless endpoint still
answers `200` with a real-looking tile, but every one of them is stamped
"API KEY REQUIRED" across the middle — a failure invisible to any status-code
check and visible only by looking at the map.

The tiles are gitignored: they are derived, a fresh clone rebuilds them in a minute,
and a repo is the wrong place for 1,700 binaries. Missing tiles degrade to the flat
background, the same thing the basemap toggle does, so a clone that skips the step
still works. Before launch, swap the source for a self-hosted Protomaps PMTiles
extract — one file read by HTTP range, rather than 1,700 loose JPEGs. Attribution
stays required either way.

**Three layers, two opacity sliders.** Basemap, area fills, density surface. At full
opacity the fills bury the raster, which is how people conclude the hotspot layer is
broken. Fills default to 80% and both layers are adjustable.

**The map failing does not break the page.** WebGL2 can be unavailable — an old
browser, a hardened profile, a CI runner. `MapView` contains that failure and shows
a message; every table, statistic and control keeps working.

**MapLibre's worker needs an explicit URL.** `src/main.js` calls `setWorkerUrl`
with a worker Vite actually emits. maplibre v6 otherwise derives the path from a
runtime `import.meta.url` — a pattern no bundler can see — and asks for a sibling
`maplibre-gl-worker.mjs` that was never built. A dev or preview server answers
that request with `index.html`, and the worker dies parsing HTML as JavaScript.
Nothing reports it: raster layers keep working, so the basemap looks fine, while
every GeoJSON source stays `isSourceLoaded() === false` forever and the fills and
boundaries never appear. `npm run inspect` catches this — `srcFeatures: 0` with a
`canvas: true` is the signature.

**Effects read their inputs before they bail out.** The area layers are added
asynchronously, after `getGeo` resolves, which is always after the map's `load`.
An effect that checks `map.getLayer('areas-fill')` before touching `rows` returns
on its first run having registered no dependency on `rows` — so when the data
lands, nothing re-runs it and the choropleth stays flat at `NO_DATA`. The paint
effects in `MapView.svelte` therefore read every reactive input into a local
first, and wait on a `layersReady` rune rather than on a plain `let`.

**State lives in the URL.** `#/s/beridze?geo=dis&metric=lq` is the whole application
state. Hash routing because GitHub Pages has no server-side rewrites.

**Rates and quotients are computed in the browser** from counts plus `areas.json`,
which is what keeps the bucket files small.

**The 1997 book stops at municipality**, so the district toggle is genuinely
disabled for it rather than silently returning nothing.

## Deploying

```bash
npm run deploy
```

Builds locally and force-pushes `dist/` to `gh-pages` as a single orphan commit,
then tells you to point Pages at that branch. `--dry-run` stages without pushing.
The repo name is read from `origin` and becomes the base path, since a project
site is served from `/<repo>/`; set `BASE_PATH=/` for a user site or a custom
domain.

The branch is rewritten from nothing every time rather than added to. That is the
whole point: the payload is ~75 MB across 515 files and the tile cache another
7 MB, all derived, all rebuilt by `npm run data` in under three minutes. Commit
that to the main branch and its history grows by that much on every refresh,
permanently. As an orphan commit, `gh-pages` always holds exactly one revision.

Git LFS is not an alternative — Pages serves LFS pointer files, not their
contents.

What is committed is code, the two boundary files, the translations, and the
small inputs (`areas.csv`, `precincts.csv`). The two large input tables are not:
`voters_surname_precinct.csv` and `surnames_meta.csv` are 39 MB between them and
are themselves derived, by `datasets/prepare_data.R`, from the roll.

`.github/workflows/deploy.yml` is the other route — build everything in CI — kept
but manual-only, since it needs those two files present. If you want push-to-
deploy later, attach them to a Release and have the workflow fetch them; that
keeps history flat while still building in the cloud.

## Known gaps

- Boundaries are synthetic Voronoi cells, not real administrative geometry.
- The Georgian locale is about a third translated; the rest falls back to English
  by design. `data/README.md` has the one-liner that lists what is outstanding.
- ~~Fonts load from Google Fonts.~~ Done: `src/fonts` holds one variable woff2 per
  subset (latin, latin-ext, georgian — 80 kB total), declared at the top of
  `src/app.css` and refreshed by `npm run fonts`.
- The production payload format (a single concatenated `kde.bin` read by HTTP
  range) is not implemented; the prototype uses the per-bucket JSON form, which is
  the documented reference anyway.
- No CSV or PNG export yet.
